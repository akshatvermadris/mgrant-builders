The Medium Has Changed. The Skill Hasn't.

Before, designing meant opening Figma and coding meant opening VS Code. Now both happen through a terminal, via Claude Code, Codex CLI or similar. The medium changed. The capability didn't. Coding is still coding and design is still design.

Quick check: someone asks "what is your medium of working?" What's the right answer?
The terminal. "Claude" is a tool, not a medium. CLI is a capability: Slack CLI and Notion CLI just mean those tools can now be driven from the terminal. The terminal is the medium everything runs through.

How we ended up back at the terminal

Tap each era.

Why AI went back

For an AI, clicking is expensive: it has to see the screen, find the button, then click. Running a command is one step. So the moment AI arrived, we all went back to the terminal, only now AI speaks the terminal's language for us, and we speak plain English to the AI.

Not comfortable in the terminal? Use Cowork, a friendlier UI that Anthropic built over the terminal. The first permission it asks for is terminal access, because underneath, it's still working in the terminal.

Vibe Coding vs AI-Assisted Engineering

No one has taught any tool how to design, code or write. You are the one doing that. So if someone tells you "you're just vibe coding", the answer should be no. If you are vibe coding, you're doing it wrong.

Vibe coding

Open-ended. "Go with the flow."
  • The AI decides the approach, usually the most common one
  • You may not know the technical route it chose
  • It spends its own time finding a palette, becoming a "colour expert"
"This dashboard card doesn't look nice. Improve it."

AI-assisted engineering

Specific. Rules, references, checkpoints.
  • You know what needs to be done and say exactly that
  • You give it your protocols: security, patterns, token-efficiency
  • You ask to see the plan before it acts
"Take the primary, secondary and tertiary palette from this website and apply it to the dashboard. Show me before you do it."

The one exception: leaders can vibe code, because what matters there is imprinting years of experience and ideology into the AI's thinking. For us, delivering client work, it has to be AI-assisted engineering.

A word on tokens

A token is the unit AI companies bill on, roughly a word or part of a word. It is a made-up unit, not a fundamental truth like binary 1s and 0s. It exists to meter usage, which also reflects electricity and compute. Your 5-hour and weekly session windows are limits measured in tokens.

Fact check: In English, one token averages about ¾ of a word, and longer or rarer words split into several tokens. How Anthropic sets weekly limits isn't published in detail, so read the "it's dynamic week to week" point from the session as an informed opinion. The practical lesson holds either way: specific prompts spend fewer tokens.

Rules, Patterns & Axioms

Good code isn't one person's vibe. When a senior engineer knows what good code looks like, they know a pattern. You don't need to memorise it. Learn it from them, then put it both in your model and in your own memory, so each can double-check the other.

Our job across these sessions is to find those patterns, algorithms and keywords, and encode them.

"Knowledge is patterns. Knowledge is not memorised words from four engineering books." Said in the session
Axioms

Some rules are constant truths. They don't change whether you're on Frappe today, Tally tomorrow or Zoho the day after. Find the reason behind a rule, and you can work any way you like as long as the fundamental truth holds.

Example core rule: form field configuration belongs in code. It must not be overwritten with every release, because that's wasted work. Make it a core rule once, and it never happens again. If it ever does, you'll catch it.

Start your own rules file

Everyone should have their own customised rules, based on truths. Share them if you want. Change the conversation from "I don't have rules, give me yours" to "here's my rule, what's yours?"

# My Engineering Rules — [Your Name] ## Layer first - Before fixing anything, classify it: data, code or infra. - Ask the 3 deduction questions before touching anything. ## How I prompt - No open-ended asks. State what, where, and the reference to follow. - Show me the plan before making changes. ## Core rules (axioms) - Form field config lives in code; never overwritten on release. - [Add the rules you learn from seniors here] ## Patterns I've learned - [Pattern] — [Why it exists] — [Who taught me]

Why this matters: across the industry, the competition is now how well the rules are encoded in your system compared with someone else's. Whose setup produces better code, faster?

The Three Layers of Digital Technology

"Technology" isn't the same as "digital". Technology is simply a way, pattern or algorithm of doing things, even the way someone parks a car. Digital technology, whether hardware or software, always has three layers. Each one is a separate skill and a separate profession, and today we're doing all three.

The house

Mum builds the kitchen wall with a recess, and the microwave fits into it. The structure complements the capability. It doesn't matter which came first; each has to fit the other. Storing photos and videos in the database without S3 is like putting the fridge on a table. The table will hold for a while, and then one day it breaks.

Edge case: Frappe fixtures. They're stored in the database, so by "every definition" they're data. They aren't: a fixture defines a form, which is a capability. Where something is stored doesn't decide its layer. What it does does.

Code isn't C++ or Java. Excel formulas are code. So is plain English to an AI. If you're changing the capability of something from X to Y, you're coding.

Deduction: Which Layer Is the Bug In?

Our biggest time sink: about half of the time goes into working out which layer an issue belongs to. One person tells the next, who tells the next. People spot a problem in one layer and "fix" it in another. Once you know the layer, the fix path is usually straightforward:

C

Code issue → go to GitHub, raise a PR.

D

Data issue → get DB or API access and correct the records.

I

Infra issue → servers, URLs, storage, security. Take it to the infra owner.

Try it: the client says…

Client
"My Output table isn't working. It was working before."
1
Can you see the other tables and pages?
Is the house standing at all?
2
Does this same table work in other projects?
Is the capability broken everywhere, or only here?
3
Are the numbers in it what they should be?
Is the capability being used with the right inputs?

Always also ask the history question: "Was it working before? What changed?" A new release or migration since then points you straight at what moved.

This is the simple version, and real problems will be tougher. But the order holds for anything: a feature, a defect, a change request, a client issue, even "Mum's Google isn't working". Classify first, then tackle. Each layer's approach gets its own focus session.
